# Shell theme contract

Status: Implementation specification; reference values retain the named owner corrections, including the white-light fixture correction in white-ink-foundation.md, and the four observed low-contrast uses resolved by three approved decisions recorded below. Every normative pair this spec declares clears its minimum without a waiver. The focus ring follows `[data-theme]` and is gated on every ground it is claimed to clear, in all three themes; "Focus indication on the themed grounds" carries the rule and the measurements.

Provide complete light, dark and black semantic maps for the collaborative shell. Preserve the existing token paths, CSS declarations and static preset keys. The new API is opt-in: `--c-*` custom properties and matching `c-*` Tailwind colors follow `[data-theme]`; the unthemed default is light. Nested theme boundaries must redeclare every role. Theme selection, persistence and system preference belong to the consumer.

The frozen fixture contains 79 theme roles: the 49 transcribed from the product reference, with the two decided hover values recorded under "Decided observed combinations" — together with the owner-approved white-light page, sunken and page-grad values documented in [White-light foundation](white-ink-foundation.md) — followed by the thirty roles the reference does not carry, recorded under "Roles added beyond the reference". The source content SHA-256 is `4470c8bab0d89444a423e6fd9597d27ce71ebe39f507882660abaf0a47539694`. Only token values are reproduced. Semantic tokens reference primitive tokens; color literals never enter the semantic tier. Gradients use [DTCG stop lists](https://www.designtokens.org/tr/second-editors-draft/format/#gradient), retaining the package’s hex-color dialect, with a namespaced `app.samourai.css-gradient` extension for the CSS angle. Generation preserves the reference API with those named value corrections. The white-light correction supersedes the earlier page-ground values and figures below; its specification records the current page measurements. Gradients belong to background images, never Tailwind colors. Repository-wide format migration remains a separate task. Translucent shadow colors remain colors, not full box shadows.

Required shell geometry: rail 76px, rail item 56px, contextual sidebar 264px, document column maximum 780px and minimum 360px, conversation dock 340px with 24px edge offset. Use named spacing tokens, with semantic and component aliases. Do not treat phone artboard dimensions as responsive breakpoints. Existing font families and typography remain unchanged; the reference's 26px title versus the earlier title rule remains a separate design decision.

Before adding source tokens, register contrast cases for new colors. Running text requires 4.5:1; meaningful non-text indicators require 3:1. Record exact low-contrast reference values without editing existing exceptions, inventing new waivers, lowering thresholds or weakening checks. Decorative borders, shadows and unsupported color combinations receive separate non-normative measurements with explicit purposes in `contrast-pairs.json` under `measurements`. So does a value this package ships but does not gate, where the figure can be computed and no threshold applies to it: the outer tone of the on-inverse ring is recorded that way. They are reported by the theme contract self-test; they do not become requirements or waivers. Normative rows measure observed text at 4.5:1 and informative icons at 3:1. Low normative ratios remain blocking failures.

Acceptance: `node --test test/theme-contract.selftest.mjs` must prove exact fixture values, identical role sets, complete scoped CSS, dynamic Tailwind bindings, geometry, determinism, dependency-free generation and fail-closed behavior for incomplete maps. Mutation controls remove a theme/role, change a reference value, delete a CSS declaration, freeze a preset color and change geometry. The ring's own coverage is proven in `test/color-math.selftest.mjs`: every ground named in the table below must carry a normative row, and five mutations — a dropped ground on each variant, a role with its theme stripped out, a loosened minimum, and a halo row with its inversion removed — each assert the message the check prints. The existing `npm test` gates remain mandatory. A green contract test does not override a red contrast gate and does not establish rendered accessibility.

## Consumer API

Import the generated CSS once. Place `data-theme="light"`, `data-theme="dark"` or `data-theme="black"` on a theme boundary. Use `bg-c-surface`, `text-c-ink`, `text-c-accent-ink` and `bg-c-page-gradient`; `bg-c-page` is the flat page color. The gradient key is deliberately distinct from the color key. Geometry is available as `w-shell-rail-width`, `w-shell-sidebar-width`, `max-w-shell-document-max-width`, `w-shell-dock-width` and direct `--shell-*` custom properties. The consumer must separately specify responsive behavior; a width token is not a breakpoint.

Two usages are decided, not free: the selected room row draws its icon in `c-ink-3` (unselected rows keep `c-ink-4`), and the connected-room indicator on the inverse panel uses `c-ok-on-dark`, not `c-ok`. The register measures those usages; a consumer that renders the reference roles instead re-creates a failure the gate no longer sees.

Existing static keys such as `text-ink` do not acquire a new theme automatically. Migrating a component to `c-*` requires auditing all its surfaces, text and statuses together. Focus indication moved ahead of them: the ring follows `[data-theme]` on its own, and the only choice a component still makes is which variant it draws. The ring's two-tone construction is decided outside this spec and moved with ADR-0002 — an opaque core inside a 35 % halo — as is the selected-control ring's own width token. This package does not certify a consumer by changing its theme attribute.

### Focus indication on the themed grounds

**The focus ring follows `[data-theme]`, in two variants, and every ground it is claimed to clear carries a normative row at 3:1.** `--focus-ring` and `--focus-ring-on-inverse` are declared inside each theme block, the light pair on `:root` as well, so a page that sets no attribute keeps a working ring. The preset's `ringColor` keys are `var()` references to the same two properties — `ring` and `ring-on-inverse` — rather than values, because a hex there would freeze one theme's ring into every theme. `test/theme-contract.selftest.mjs` holds the preset to that: one key per variant and no others, each key a reference to the custom property that variant declares, and that property declared in the generated CSS. The CSS side is pinned by literal value in every theme block; the drift gate cannot pin the preset side, because the generator and its output move together.

The rule is uniform; no theme is a special case.

| Variant | Opaque core | The grounds it is drawn on |
|---|---|---|
| `--focus-ring` | `semantic.theme.<t>.accent-ink` | the seven shell containers — `surface`, `sunken`, `page`, `hairline`, `muted`, `muted-2`, `elevated` — and the twenty-two painted backgrounds: `accent-soft`, the `ok`, `warn` and `bad` softs, `t1-bg` through `t6-bg`, `cursor-1-soft` through `cursor-6-soft`, and `tag-1-bg` through `tag-6-bg` |
| `--focus-ring-on-inverse` | `semantic.theme.<t>.on-inverse` | `inverse`, `inverse-2` and `bad`, where the normal core is the wrong side of the ground |

Measured with this package's own colour maths, the core clears 3:1 on every one of those grounds, in every theme:

| Theme | Core on the twenty-nine normal and painted grounds | On-inverse core on `inverse`, `inverse-2` and `bad` |
|---|---|---|
| light | 6.39:1 – 8.07:1 | 5.42:1 – 11.59:1 |
| dark | 7.18:1 – 9.81:1 | 5.03:1 – 17.62:1 |
| black | 8.95:1 – 11.24:1 | 5.17:1 – 20.03:1 |

The worst case on the normal and painted grounds is 6.39:1 (`light.muted-2`) and on the on-inverse grounds 5.03:1 (`dark.bad`), against a 3:1 requirement. **Ninety-six normative rows** in `contrast-pairs.json` carry those measurements — `theme.<t>/focus-ring/<ground>` and `theme.<t>/focus-ring-on-inverse/<ground>`, all at `min: 3.0`, none exempt, none inverted, none allowlisted. They read the ring through the `spec:focus-ring.<theme>.indicator` and `spec:focus-ring-on-inverse.<theme>.indicator` roles rather than a token path, so re-theming the ring, or moving its layers, moves the rows with it. The two rows that measure the ring against the unthemed `semantic.surface.*` values stay, reading the light role: `focus-ring/surface.default` 8.07:1 and `focus-ring/surface.page` 7.23:1.

**The light theme's ring changes colour.** Its core moves from `#2B4BDB` to `#2340C4`, which is a real if small change to the default theme — on white it goes from 6.70:1 to 8.07:1. Nothing else a consumer already renders moves.

**What this replaces.** The core was `semantic.action.primary` (`#2B4BDB`), one value under every theme attribute. It measured below the 3:1 SC 1.4.11 asks of a focus indicator on all eight shell grounds of the dark theme (2.06:1 to 2.83:1), on five of the black theme's eight (2.49:1 to 2.92:1) — and, recorded in no document until this change, on two of the light theme's own: `light.inverse` 1.73:1 and `light.inverse-2` 1.37:1. The light theme was not exempt from that: it was simply never measured on the two grounds where it failed. The four non-normative `measurements` rows that recorded part of the dark and black shortfall are retired with it: they existed because there was no themed alternative to reach for, and there is one now.

`semantic.theme.<t>.action` was measured as a candidate core and rejected: it clears only three of the dark theme's eight shell grounds.

**The halo is still not the indicator.** The default ring's 35 % halo stays below 3:1 on all ninety-six theme-and-ground combinations it was measured over, from 1.01:1 to 2.27:1 (`elevated` adds 1.86:1, 2.25:1 and 2.27:1), and four inverted `expect: "fail"` rows pin that — two on the unthemed surfaces, one each on `dark.surface` (2.27:1) and `black.surface` (2.20:1). If one of them ever clears 3:1, the two-tone construction is doing nothing and someone has to say which tone the indicator is. The on-inverse ring's halo is the exception, and it is stated rather than smoothed over: it reaches 3.04:1 on `dark.inverse` and 3.15:1 on `black.inverse-2`, so it carries no inverted row — one asserting it stays below 3:1 would be false — and is reported instead by nine non-normative `measurements` rows, `focus-ring-on-inverse-halo/theme.<t>.inverse`, `…/theme.<t>.inverse-2` and `…/theme.<t>.bad`, one for each ground in each theme, so all of those figures are derived by a row here rather than copied into this sentence. In both variants the indicator is the opaque core, and the opaque core is what the normative rows gate — except on `dark.inverse` and `black.inverse-2`, where a translucent-only ring would clear 3:1 on its own row and the gate would report a PASS. What holds the guarantee there is an invariant rather than a row: `test/color-math.selftest.mjs` asserts that the tone against the control is opaque, on every theme and every variant.

**What the coverage check proves.** `test/color-math.selftest.mjs` derives the grounds from the theme roles themselves rather than from a list written beside them, so a ground added to the themes later has to carry a ring row, and a role the classification rules cannot place stops the suite by name instead of falling silently outside the claim. It derives the variants from `SPEC.focusRing.variants` for the same reason: a variant added there composes tones that must carry rows before the ring it paints can ship. What it does not prove: the inverted halo rows are one per theme, not one per ground, so they pin that the halo is never the indicator in each theme without restating the 1.01:1 – 2.27:1 spread across all ninety-six combinations. And no row measures the ring against the **control** it surrounds, in either direction. In the light theme the core `#2340C4` is `light.action-hover` exactly, so a focused primary button draws its ring at 1.20:1 against its resting fill and 1.00:1 against its hovered one — invisible on hover; dark and black draw 3.12:1 and 3.59:1 on the same two fills. The control fills are listed among the non-grounds in that file so the gap is recorded rather than left implicit; closing it belongs to the control spec, not here.

**Owner decision `B-themed-ring` is closed by this change**, in the direction the record left open: the ring gained themed variants rather than the shortfall being accepted with a stated reason. Nothing here waives anything, exempts a row or lowers a threshold.

## Roles added beyond the reference

The reference draws no menu, dialog, form field or disabled control, and the product needs all four. Six roles close that gap in every theme. Alongside them, twenty-four roles close the two palette gaps recorded in the product reference (`p06-docs.html`, where collaborator 2's cursor fell back to `ink-4` because only one accent existed, and `t1`–`t4`, where categorical tags reused the semantic status tints): twelve collaborator cursor roles (`cursor-1`..`cursor-6` and `cursor-1-soft`..`cursor-6-soft`) and twelve non-status categorical tag roles (`tag-1-bg`/`tag-1-fg`..`tag-6-bg`/`tag-6-fg`). All thirty are additions, not deviations: no reference value moves, and the fixture lists them after the 49 reference roles.

| Role | What it is for | Light | Dark | Black | Gated by |
|---|---|---|---|---|---|
| `elevated` | Menus, popovers, dialogs, the command palette. Lighter than `surface` in dark and black, because a shadow alone does not read on a dark ground | `#FFFFFF` (= `surface`) | `#1D252E` | `#141619` | `ink`, `ink-2`, `ink-3`, `accent-ink`, `ok-ink`, `warn-ink`, `bad-ink` at 4.5:1; `ink-4` icons and the focus ring at 3:1 (it is a shell container) |
| `scrim` | Overlay behind a dialog or a mobile drawer | `rgba(47,58,69,.55)` | `rgba(0,0,0,.6)` | `rgba(0,0,0,.72)` | Decorative `measurements` row on `page`; it carries no meaning |
| `border-input` | The edge of a control the user has to find: field, checkbox, select | `#7C8894` (= `slate.500`) | `#6B7886` | `#606A75` | 3:1 on `surface`, `sunken`, `muted`, `elevated` (worst 3.21:1, 3.31:1, 3.26:1) |
| `placeholder` | Input hint | `#5C6874` (= `ink-3`) | `#8592A1` | `#7C8794` (= `ink-4`) | 4.5:1 on `surface`, `sunken`, `muted`, `elevated` (worst 5.06:1, 4.71:1, 4.92:1) |
| `disabled` | Fill of a disabled control; neutral, never the action colour | `#EEF2F6` (= `muted`) | `#242E38` (= `muted-2`) | `#1B1E22` (= `muted-2`) | Through `on-disabled` |
| `on-disabled` | Label on the disabled fill | `#5C6874` (= `ink-3`) | `#98A6B5` (= `ink-3`) | `#9BA7B4` (= `ink-3`) | 4.5:1 on `disabled` (5.06:1, 5.55:1, 6.83:1) |

**On `elevated`, status draws its `-ink` role.** A destructive menu item, an error icon or a success mark in a dialog uses `bad-ink`, `ok-ink` or `warn-ink`, gated at 4.5:1 (worst 5.91:1, light `warn-ink`). The fill roles `ok`, `warn` and `bad` are gated as 3:1 indicators on the base grounds only (`surface`, and the softs). Dark `bad` drops below 3:1 on `elevated` (2.86:1), so menus and dialogs switch every status to its `-ink` role rather than deciding colour by colour. Three `capability` measurements per theme report what the fills would measure there, so the gap is visible rather than gated: a consumer that draws `c-bad` as an icon on a menu re-creates it. The fills are also ungated, and below 3:1, on other grounds a consumer might reach for: dark `bad` on `muted` 2.76:1, `muted-2` 2.54:1, `hairline` 2.96:1 and `accent-soft` 2.79:1, light `warn` on `muted-2` 2.88:1. An indicator on one of those draws its `-ink` role too.

`border-input` and `placeholder` are claimed on four grounds only — `surface`, `sunken`, `muted`, `elevated` — because a field is drawn on those and nowhere else. Light `border-input` measures 2.86:1 on `muted-2` and 2.99:1 on `accent-soft`, and dark `placeholder` 4.35:1 on `muted-2`; a field placed on one of those needs its own row first.

The decorative border roles (`border`, `border-soft`, `border-strong`) stay decorative: a component whose only boundary is its edge draws `border-input`. A disabled control is told apart by its neutral fill, the absence of a border and the absence of the action colour, not by a faded label — in light, `disabled` is the `muted` value, so a secondary control always draws its `border-input` edge and a disabled one never does: WCAG exempts disabled controls from 1.4.3, and the label clears 4.5:1 anyway. The unthemed `semantic.text.placeholder` moved the same way, from `slate.500` (3.62:1, exempt) to `slate.600` (5.87:1 on white, 5.22:1 on the muted field), so neither placeholder row needs an exemption any more.

## Decided observed combinations

The hashed reference carried four observed uses below their normative threshold. The design owner resolved them with three decisions that reuse colours already in the palette; no waiver was added, no row was exempted and no threshold moved. `tokens.json` and the fixture carry the decided values; the reference hash above is unchanged.

| Observed use | Decision | Foreground / background | Before | After | Required |
|---|---|---|---|---|---|
| Dark button hover label | `action-hover` maps to the shared `cobalt.500` | `#F3F7FB` / `#4C6BF0` → `#F3F7FB` / `#2B4BDB` | 4.178579:1 | 6.228601:1 | 4.5:1 |
| Black button hover label | the same shared mapping | `#F7FAFC` / `#4C6BF0` → `#F7FAFC` / `#2B4BDB` | 4.291349:1 | 6.396695:1 | 4.5:1 |
| Light selected-room icon | the selected row's icon uses `ink-3` | `#7C8894` / `#E4E9FB` → `#5C6874` / `#E4E9FB` | 2.987678:1 | 4.704526:1 | 3:1 |
| Light connected-room dot | the indicator on the inverse panel uses `ok-on-dark` | `#2E8B57` / `#2F3A45` → `#A8E5C4` / `#2F3A45` | 2.730008:1 | 8.095806:1 | 3:1 |

Decision 1 is a value change. `semantic.theme.dark.action-hover` and `semantic.theme.black.action-hover` reference `color.cobalt.500`, and the rejected `color.theme-dark.action-hover` and `color.theme-black.action-hover` primitives are removed so the value leaves the source rather than surviving as an unused variable. The idle fill stays `action` (`#3B57DE`); hover now darkens instead of lightening. The light theme is unchanged.

**Decision 1 is a deliberate deviation from the mock, reaffirmed.** The high-fidelity mock (design handoff, "Couleurs — thème sombre" and "thème noir") draws `--c-action-hover` as `#4C6BF0`. On 2026-09-24 the owner ruled to keep `#2B4BDB`, superseding a same-day ruling to take the mock's value, for the reason in the first two rows of the table above: under `#4C6BF0` the button label on hover drops to 4.18:1 (dark) and 4.29:1 (black), below 4.5:1.

Decisions 2 and 3 are usage changes, not value changes: `ink-4`, `ok`, `ink-3` and `ok-on-dark` keep their reference values. The register rows for the two observed uses measure the decided roles, `theme.light/icon-ink-3/accent-soft` and `theme.light/indicator-ok-on-dark/inverse`, and the rows for the retired uses (`ink-4` on `accent-soft` and `ok` on `inverse`, light theme) went with the uses; their measured ratios are the "Before" column above. Unselected room rows keep `ink-4` on `surface`, `sunken` and `muted`, which stay measured at 3:1. The dark and black connected-room rows keep `ok` on `inverse`, which clears 3:1 in both; a consumer that uses `c-ok-on-dark` for the indicator in every theme is covered by the existing 4.5:1 `ok-on-dark` text rows.

Source anchors in the hashed reference: buttons at lines 342, 1758 and 2636; room icon at 203 with selected background assigned at 3003; connected-room dot at 294. The ratios use unrounded WCAG luminance comparisons; a displayed rounded value does not turn a failure into a pass.

The unsupported running-text and sole-boundary capability measurements are reported separately. They are not new release requirements, not exemptions and not reasons to redesign decorative elements.
